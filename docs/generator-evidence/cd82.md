## Authoritative source and complete mechanics

The audit used the vendored native source
`third_party/arc3_games/cd82.py` at snapshot
`fcb364382df0ecfbe1d3976bb05f18c0b0262fea` (source SHA-256
`dafeabff60a3a99b5c93629f8da0d8f555b873ef16a522247d6197b1b3addbcb`).
There are exactly six official levels (`cd82.py:257-361`).

All official rule mechanics are represented:

- Four movement actions move a dial around eight positions of a 3x3 ring;
  moves off the ring or into its centre are charged no-ops
  (`cd82.py:393-412,531-549,642-658`).
- ACTION5 animates the active basket, then paints one of four edge halves or
  four corner triangles using the selected colour
  (`cd82.py:393-402,659-662,673-738`).
- ACTION6 clicks one of the displayed colour swatches and moves the cursor;
  actual native display coordinates are used (`cd82.py:551-572,755-764`).
- Tiers 3-6 contain an indicator. At an edge dial, clicking it animates and
  paints the corresponding 3x4 cap strip. The indicator moves/rotates with the
  active basket and disappears at corner dials
  (`cd82.py:495-628,663-669,766-777`).
- The canvas starts black, the selected colour starts at 15, and the dial
  starts north at position 0 (`cd82.py:414-415,447-463`).
- Win comparison uses the 80 cells outside both diagonals; the 20 diagonal
  cells are visually present but ignored (`cd82.py:740-753`).
- The native loss threshold is action 100. Exactly 99 actions are usable;
  level changes reset the counter (`cd82.py:431,447-463,630-635`). Basket and
  cap animations remain native because every witness is replayed through
  `Cd82.perform_action`, not a symbolic substitute.

CD82 has no undo mechanic. Live-prefix replanning and ACTION0 reset recovery
are tested instead.

## Procedural generation and proof

- Tiers 1 and 2 uniformly sample rule-derived native atom-state closures: 122
  reachable binary states for tier 1 and 1,275 reachable three-colour states
  for tier 2. These closures are computed from native paint masks; they contain
  no official target or stored route.
- Tiers 3-6 sample new operation positions, order, colour assignment, palette
  order and resulting target composition using the tier's measured
  half/triangle/cap recipe. Exact solution gates decide admission.
- Every candidate is structurally recomputed, searched within its fixed tier
  cap, rejected on truncation, checked against the action tolerance and
  mechanic-use floor, then replayed with actual click coordinates in a fresh
  six-level native engine at context `difficulty - 1`.
- `validate_full_standard` recomputes structural metrics, all canonical
  identities/partition, route mechanics, and the native winning outcome. It
  rejects malformed actions, stale nested proof fields, early wins,
  same-length wrong routes, wrong budgets/contexts and official-equivalent
  targets without rerunning full search.
- `generate_game` derives child seeds with BLAKE2 from canonical source ID,
  game seed, ordinal and difficulty. `build_game` rejects empty/short/extra,
  out-of-order, duplicate, mixed-split or context-shifted curricula and then
  replays all six levels without `set_level` or any forced transition.
- Rejection attempts and typed reasons are bounded and retained. A search cap
  is always `search_truncated`, never called an impossibility proof.

## Identity, split and finite support

Identity version `cd82-semantic-color-d4-v2` makes all three stored hashes use
the same executable-puzzle vocabulary. They ignore the 20 non-compared
diagonal cells, numeric colour names, palette ordering, and private fields such
as seed, solution and proof, while preserving the compared-cell colour
partition, indicator presence, palette cardinality and orientation.
`geometry_d4_sha256` additionally canonicalizes rotations/reflections and is
used consistently for split assignment and official-copy rejection. V2 hashes
are domain-separated; their deterministic nonce retains each established v1
modulo-three split bucket without retaining a v1 digest or changing the
equivalence relation.

An exhaustive tier-1 closure audit found 122 reachable native atom states, 56
profile-shaped states/orientations, and only five total D4 target classes. Once
official-copy, 4-8 action and meaningful-half gates are applied, every split
has exactly one accepted D4 class. Orientation-preserving bank capacities are
train 6, validation 6 and test 4. Rotations remain gameplay-relevant because
the dial starts north; they are not claimed as new canonical structure.
Single-tier bank building reports this finite cap and stops targeting counts
beyond it. The shared whole-game pipeline may repeat the tutorial D4 class
within a split while deduplicating whole games and enforcing cross-split D4
separation.

Review-2 hardening validates every emitted base and optional episode context,

Python boolean/float aliases, contradictory native outcomes, malformed nested
mappings and stale identities all reject. Eighteen focused tests passed in

native witness replay, live prefix/reset recovery and truncation handling.
Live recovery is separate coverage: the final unperturbed primary collection
correctly reports only certified-solution execution and does not inherit stored

Material limitations remain:

1. Six profiles are calibrated from one official level each; they do not show
   distributional equality to a larger unseen population.
2. Tier 1 has only one accepted D4 class per split and a 4-8 action range
   around official 5. This is explicit finite tutorial support, not broad
   structural diversity.
3. The final quality audit is a modest 18-row sample. It establishes coverage,
   bounded operation and replay, not production-scale acceptance rates.
4. Optimality is certified by the package's complete non-truncated A* search;
   native replay independently verifies execution but no second search
   implementation repeated every generated optimum.
5. D4 grouping is intentionally conservative for split exclusion. It does not
   claim action-distance invariance because orientation changes distance from
   the fixed north dial.
6. Contract status remains `pending_audit`; only root may change it to `ready`.
